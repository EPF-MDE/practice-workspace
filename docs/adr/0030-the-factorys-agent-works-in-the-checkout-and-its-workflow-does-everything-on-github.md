# The Software Factory's agent works in the checkout, and its workflow does everything on GitHub

Each run of the Software Factory is a GitHub Actions workflow that runs one agent script in `.sandcastle/agent-workflows/`. The agent reads and writes a checkout of the Engine; what it does on GitHub (pushing, opening a pull request, creating issues, commenting, labelling) could be done by the agent itself or by the workflow steps around it. **So the agent never acts on GitHub: it edits and commits in the checkout, or hands back a structured answer, and the workflow steps after it do every push, pull request, issue, comment and label.**

- **The agent holds no GitHub token.** The workflow gives the factory's token only to the steps that call GitHub, and checks the code out with `persist-credentials: false`. What reaches GitHub is in a workflow step, where the Instructor can read it. Keeping the token out of the agent's environment is tidiness, not a wall, since the agent shares the machine with those steps: the defence is who can reach the agent (ADR-0031).
- **The agent commits through the pre-commit hook.** `implement/implement.ts` and `implement-spec/build.ts` let the agent commit, so the hook runs on its work and it has to fix whatever the hook rejects; the workflow then pushes and opens the pull request.
- **A structured answer is a contract with its workflow.** Each schema the agent answers in is what a workflow acts on, and changing it means changing that workflow in the same change:
  - `explore/plan-schema.ts` (`explorePlanSchema`): the apply job of `agent-explore.yml` checks the whole plan, then branches on each entry's `tag`.
  - `implement-spec/decomposition-schema.ts` (`specDecompositionSchema`): the decompose loop writes tickets, not code. `agent-implement-spec.yml` creates one GitHub issue per entry, each carrying its `position` and the positions it depends on, and the chain then builds them one at a time, always the lowest open position whose dependencies are closed.
  - `review/review-schema.ts` (`reviewSchema`): the findings the review left unfixed. `agent-review.yml` posts each as an inline comment on its file and line, and the verdict lists it by title (ADR-0032).
- **The review run splits the same way.** In `review/review.ts` the agent fixes and commits, writes the verdict file and hands back the findings it left; the script adds those findings to the verdict; the workflow pushes the commits, posts the verdict and the inline comments, and marks the pull request ready.

## How a structured answer is asked for

Several runs need a structured answer from the agent (a plan, a queue of tickets, the findings a review left) after work that uses the whole toolset, and asking for both in one run mixes the work with the answer's format. **So `runWithExtraction` in `.sandcastle/agent-workflows/shared/run-with-extraction.ts` runs two passes over one session: the first does the work with the whole toolset, and the second resumes that session and asks only for the structured answer, extracted from everything the first pass read.**

- **The zod schema is the one place the answer's shape is written.** `extractionPrompt` in `shared/extraction-prompt.ts` prints the schema into the second pass's prompt as JSON Schema, descriptions and all, so the `.describe()` texts are the agent's instructions.
- **Retries resume the extraction session.** `maxRetries` (default 2, so three attempts) is forwarded to the `maxRetries` of Sandcastle's `Output`, which resumes the extraction session and feeds back the error so the agent can send a corrected answer.
- **An agent that cannot resume a session gets one pass.** A custom agent provider that keeps no sessions (every built-in one does) gets no second pass and no retries: the extraction instructions are appended to its prompt, and it gives the structured answer at the end of the work itself.
- **A prompt file is copied, not inlined.** `appendToPrompt` copies the prompt file with the instructions appended, so Sandcastle's `promptArgs` substitution still applies to it.
