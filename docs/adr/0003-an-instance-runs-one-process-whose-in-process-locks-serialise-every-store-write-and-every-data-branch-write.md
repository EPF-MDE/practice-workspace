# An Instance runs one process, whose in-process locks serialise every Store write and every data branch write

A Send's version is counted from the entries already stored. A drawing's files and the Repository reading's saves are both written to the Instance's data branch, and a writer that reads the branch's tip, builds a commit and moves the ref loses another writer's commit if both do it at once. **So an Instance runs one process (`uvicorn app.main:app`, one worker) holding one Store for the whole Instance, and that process serialises its writes with in-process locks: one per Student for their Sends (`GitHubStore._student_lock`), and one per repository and data branch, `app.github_app.data_branch_lock(repository, branch)`, which every writer of that branch takes.**

- **Two workers would break both.** Each would hold its own locks and its own copy of a record: versions would collide, and one worker would not see the other's Sends. Scaling an Instance out means moving these locks out of the process first.
- **A drawing's files live on the data branch.** A drawing's PNG and tldraw snapshot are too large for an issue comment, so the GitHub Store writes them as two files at the paths `drawing_paths()` gives (per Student, Competency and drawing), then the drawing's comment, which records the commit holding both: three writes per drawing Send. A new version overwrites the same two paths, so Git history keeps every version, and a drawing is read back at the commit its latest entry names.
- **The two writers share one lock.** The GitHub Store's drawings (`GitHubStore.save_drawing`) and the Repository reading's saves (`GitHubWorkspaceData.write` in `backend/app/repository_reading/storage.py`) take the same lock for the same branch; another branch gets its own. Without it, the Repository reading's commit could land between a drawing's two files, and the drawing's comment would record a commit that does not hold both. `backend/tests/test_data_branch_lock.py` guards it.
- **The Repository reading writes many files as one commit.** `WorkspaceData.write` writes every file it is given in one commit, through GitHub's Git Data API: `GitHubWorkspaceData.write` takes 5 requests whatever the number of files. The files go inline in the new tree (`content`), never as blobs created one by one, since a reading is UTF-8 JSON. `GitHubWorkspaceData.read` falls back to the Git blobs API when the contents API gives no `content`, which GitHub does for a file over 1 MB.
- **Writers outside the process are met by a retry, not by the lock.** The Repository reading's batch and the Instructor by hand also move the branch. The GitHub Store reads the branch again and retries a file write GitHub refuses with 409, a few times (`DATA_RETRIES`) with a growing pause, before the Store is unavailable and records no entry. `GitHubWorkspaceData.write` moves the ref without force; GitHub answers 422 when the move is not a fast-forward, and the write starts again from the new tip, a few times (`retries`), then fails loudly.
- **No file is downloaded to overwrite it.** The GitHub Store lists a file's current blob sha from its folder (`_file_sha`).
