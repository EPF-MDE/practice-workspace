# A Student signs in with GitHub by their numeric id, checked against the Roster on every request

A Student signs in with GitHub, and the Roster says whether they get in. A GitHub login can be renamed, and once freed it can be taken by someone else. The Practice workspace must hold no more of a Student's GitHub access than it needs, and the Instructor keeps the Roster in a spreadsheet, adds Students during a Course, and must be able to shut someone out without touching the running Instance. **So `app.auth` asks GitHub who the visitor is through the Student Connector, which requests no repository permission at sign-in; the Roster is `roster.csv` on the Instance's data branch; a Student is matched on the numeric GitHub id, never on the login; the session cookie holds that id alone; and every request finds the Student on the current Roster again.**

- **The numeric id decides.** A renamed account still gets in; someone who took over a login on the Roster after its Student renamed theirs does not. `backend/tests/test_sign_in.py` guards it.
- **No Student's token is kept.** `GitHubIdentity.identify` uses the Student's token once, to read `GET /user`, then revokes it. `backend/tests/test_github_identity.py` guards it.
- **The Roster is one CSV.** One row per Student, `github_login,github_id,name,group,project,evidence_project`. `parse_roster` accepts CRLF or LF line ends and a leading byte order mark, as a spreadsheet exports them.
- **The Roster changes without a deploy.** A deployed Instance re-reads it at most every five minutes (`app.roster.RefreshingRoster`), so the Instructor adds a Student by pushing to the data branch. If a re-read fails, the last Roster read is kept. A local run reads a Roster file instead (`roster_file`, `StaticRoster`).
- **Removing a row signs a Student out.** `current_student` reads the Roster as it is now: a Student no longer on it gets a 401 at their next request.
- **`Identity` is the seam.** `GitHubIdentity` serves every deployed Instance. `FakeIdentity`, where `/auth/login?github_id=<id>` signs that id in through the same callback, serves the tests and the local Playwright run, and `app.main` refuses it on Azure (ADR-0002).
- **A Store failure does not block sign-in.** `_open_record` asks the Store to open the Student's record at their first sign-in. If the Store is unavailable then, the Student still signs in, and their first Send opens the record.
